# ADR-0086 — Usage monitor: plan limits from the agents' own channels, a status bar, and a widget in the Windows taskbar

Date: 2026-10-19
Status: Accepted for this local fork. Builds on ADR-0002 (the agent is an embedded PTY), ADR-0005 (kill-on-quit), ADR-0036 (a profile is a config directory) and ADR-0060 (Codex behind one seam, F30). Design: `docs/superpowers/specs/2026-10-19-usage-monitor-design.md`.

## Context

People run Claude Code and Codex in factorai on a subscription and want to see, without typing `/usage`, how much of the 5-hour and weekly windows is left, and how heavy the session in front of them is. Neither CLI exposes that through a supported API. What each one does expose:

- **Claude Code** pipes a JSON object to its `statusLine` command on every refresh, and for Pro/Max subscribers it carries `rate_limits.five_hour` / `seven_day` after the first response. factorai builds the `claude` argv, so it can put a status line in front of the user's.
- **Anthropic's usage endpoint** (`/api/oauth/usage`) answers with the same windows plus per-model ones, but it is undocumented, it wants the OAuth token Claude Code saved, and Anthropic's terms restrict third-party use of Claude.ai credentials.
- **Codex** writes its limits into every rollout as a `token_count` event, and `codex app-server` answers `account/rateLimits/read` live, at no quota cost.

The place to show it is the app and, on Windows, the taskbar next to the clock, which is visible while the user is in another app. Windows has no API for putting a third-party control in the taskbar.

## Decision

- **Claude: the status line, injected with `--settings`.** A Claude session factorai spawns gets `--settings '{"statusLine":{"type":"command","command":"'<factorai exe>' --usage-statusline '<sink dir>' '<config dir>'", …}}'` — each path single-quoted with `/` separators; where Claude Code will run the status line in PowerShell (Windows without Git Bash) the command is `& '<factorai exe>' --usage-statusline '<sink dir>' '<config dir>'`, with PowerShell's doubled-quote escaping. That command is **factorai's own binary in a helper mode**: `main.rs` checks for the flag before any Tauri code runs, writes the payload's `rate_limits` to `<data_dir>/usage/statusline/<session>.json` (temp file and rename) together with `<config dir>` — the profile's config directory as factorai stores it, so the reading is filed under the right profile even when the session resolves a different `CLAUDE_CONFIG_DIR` (the helper still accepts the older two-argument form and then names the directory the session reads), then runs the user's own `statusLine` (project `settings.local.json` > project `settings.json` > the profile's `settings.json`) with the same stdin and prints what it printed. No network, no POSIX shell required, never fails loudly. The poller reads the sink files and maps them to profiles by config directory, logging once a directory that matches no profile.
- **The injection is on by default and has a setting to turn it off** (`usageStatusLine`, `usage.statusline`: unset → on, `off` → off). With it, a user who has **no** status line of their own loses Claude Code's footer hints, because a configured status line replaces them; the setting is how they get the hints back, at the cost of Claude's numbers.
- **The first time factorai reads a credential: opt-in, read-only, never refreshed.** Only when `usageClaudeEndpoint` is `on` (off by default, with the terms warning in Settings) does factorai read `<config dir>/.credentials.json` for the access token and call `GET https://api.anthropic.com/api/oauth/usage` with redirects disabled (the token never follows a 3xx elsewhere; a 3xx backs off like a 429), at most every 5 minutes per profile, honouring `Retry-After`. An expired token is reported and the profile skipped until Claude Code renews it itself: factorai never writes the file, never calls a token endpoint, never logs the token. Codex's `auth.json` is never read.
- **`codex app-server` may refresh Codex's own token, and that is accepted.** factorai runs `codex -s read-only -a never app-server` per Codex profile with its `CODEX_HOME`, at startup and every 5 minutes, with a 15 s timeout and the process tree killed on every exit path. If the token has expired, Codex's own code refreshes it, exactly as a second Codex session under the same `CODEX_HOME` would. factorai still neither reads nor writes `auth.json`.
- **`ureq` is the backend's first HTTP client**, for that one blocking GET on the poller thread: default features (rustls), the body parsed with `serde_json`. Not `reqwest`, because nothing else needs an async client and one call does not justify a second runtime's worth of dependencies.
- **Usage Amber** (`--usage-warn`, DESIGN.md § Signal colours) is a new token with a single job: a plan limit is getting close (70–89%). Below 70% the bar is colourless; from 90% it is `destructive`, whose second job this becomes. The taskbar widget uses the same three bands.
- **The taskbar widget is a native layered window reparented into the taskbar** (`platform/taskbar_widget/windows.rs`), not a WebView: a `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` window whose premultiplied pixels (tiny-skia, Segoe UI through fontdue) are pushed with `UpdateLayeredWindow`, switched from `WS_POPUP` to `WS_CHILD` and `SetParent`ed into `Shell_TrayWnd`, 8 logical pixels left of `TrayNotifyWnd`, vertically centred, repositioned on `EVENT_OBJECT_LOCATIONCHANGE` from the taskbar's thread (coalesced 50 ms), recreated on `TaskbarCreated`, re-reading `SystemUsesLightTheme` every 60 s, sized from `GetDpiForWindow` of the taskbar. A click brings the main window forward.
- **One thread owns it, and nothing waits on that thread.** Cross-process `SetParent` attaches the widget thread's input queue to Explorer's, so a hung Explorer can hang it. The named `taskbar-widget` thread owns the windows, the hook and the message loop; the rest of the app reaches it only through an `mpsc` channel and a `PostThreadMessageW(WM_APP)`, never a `SendMessage`, and it takes no lock anyone else waits on. The tray fallback's Tauri calls go the other way through `run_on_main_thread`, which posts.
- **The tray icon is the contract; the embed is best effort.** Cross-process `SetParent` into the taskbar is not supported by Microsoft, and a Windows update can break it without notice. If `Shell_TrayWnd` is missing, `SetParent` or the first `UpdateLayeredWindow` fails, there is no system font, or 2 s after embedding the window is not a visible child of the taskbar, the widget logs one warning and becomes a notification-area icon (Tauri's `tray-icon` Cargo feature, Windows only): the most critical percentage drawn in its band colour, the four numbers in the tooltip, a left click focusing the main window. `FACTORAI_TASKBAR_WIDGET_FORCE_TRAY` forces it, for checking the fallback on a machine where the embed works.
- **The app manifest declares Windows 8 and later**, and on MSVC it is embedded by the linker (`build.rs`) rather than by tauri-build's resource file. Windows honours `WS_EX_LAYERED` on a child window only for a process whose manifest says so; without it `UpdateLayeredWindow` fails with `ERROR_INVALID_PARAMETER` and the widget would be an empty rectangle. Linking it means test binaries get it too, which the tray needs: the `tray-icon` feature pulls muda's `TaskDialogIndirect`, a Common-Controls v6 export, into every binary, and one without the v6 dependency does not load.
- **Only while factorai runs, primary taskbar only, on by default** (`usageTaskbarWidget`, `usage.taskbar_widget`: unset → on, `off` → off, applied live by `set_setting`). Stopped on the quit path; if the process dies the system destroys its windows.

## Consequences

- Claude's numbers move only while a Claude session in factorai is talking; between, the bar shows the last values, persisted in `<data_dir>/usage.json` and labelled stale after 15 minutes. A window whose reset time has passed reads 0%.
- A user's own `statusLine` keeps working inside factorai, but runs through factorai's binary; a user without one trades Claude Code's footer hints for the numbers unless they turn the setting off.
- The opt-in endpoint is a grey zone the user chooses with the terms in front of them. If Anthropic changes or closes it, the official route still works.
- A Windows update that stops the embed degrades the widget to a tray icon rather than to nothing. The embed itself, the theme switch, DPI changes and an Explorer restart are verified by hand, not in CI; `embeds_into_taskbar` is an ignored test that needs a real taskbar.
- The widget is placed for a horizontal taskbar. A vertical one (Windows 10 allows it) gets a widget that is visible, so the 2 s check passes and no fallback happens, but misplaced; vertical and secondary-monitor taskbars are out of scope.
- The manifest change applies to the whole app: it now runs with Windows 10 behaviour rather than the compatibility shims an undeclared process gets (for example, the true OS version from version APIs).
- macOS and Linux get the status bar only; the widget module is a no-op there, and Linux does not take on the appindicator dependency.
